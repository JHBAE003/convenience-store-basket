# v2.1 재고 수집 점검 기록

기록 시각: 2026-10-31T22:33:21+09:00. 원본 v2의 소스 98개를 별도 폴더에 복사한 뒤 이 폴더에서만 변경했다. GitHub 업로드·배포는 하지 않았다.

## 실제 코드와 기존 설명의 차이

- v2는 브랜드별로 `DaisoMcpAdapter`와 `CompositeInventoryAdapter`를 항상 두 개의 작업으로 실행했다. CU·GS25·세븐일레븐은 두 경로가 대부분 같은 `mcp.aka.page`에 연결되므로 독립된 출처가 아니다. 이마트24 보조 경로만 공식 재고 API 직접 요청을 포함한다.
- v2의 `core/config.py` 기본 재고 TTL은 1,800초였지만 `new_session_manager()`가 300초로 덮어써 실제 화면은 5분이었다. 행사 관리자의 기본값은 6시간이었다.
- v2는 응답 완료 시각이나 HTTP `Date - Age`를 재고 자료 시각으로 사용하는 경우가 있었다. v2.1은 이 추정을 제거했다.
- 숫자로 된 브랜드 상품 코드를 공통 바코드로 추정하는 경로가 있었다. 명시적인 `barcode/ean/gtin/upc` 필드만 공통 바코드로 사용하도록 변경했다.

## 경로 선택과 호출 계약

| 브랜드 | 선택 상품 주 경로 | 보조 경로와 사용 조건 | 분리의 한계 |
| --- | --- | --- | --- |
| GS25 | 통합 MCP `check_inventory(service=gs25, itemCode=선택코드)` | 주 경로 오류·명확한 누락·해석 불가 때 기존 REST 재고 요청 | 선택 코드가 있으면 검색을 건너뛴다는 스키마를 확인했다. 두 경로는 같은 중계 서비스다. |
| CU | 통합 MCP `check_inventory(service=cu, keyword=선택명)` | 같은 조건에서 REST 재고 요청 | 공개 `search_products`가 CU를 지원하지 않는다. 상품 후보와 첫 후보의 점포 재고가 함께 온다. 후보 화면에서는 재고를 확정 사용하지 않는다. 선택 코드가 첫 후보가 아니면 목록에서 찾은 오프셋으로 그 상품만 다시 요청하고 응답 코드를 검증한다. |
| 세븐일레븐 | 통합 MCP `check_inventory(service=seveneleven, keyword=선택명, storeKeyword=지역)` | 같은 조건에서 기존 REST 재고 요청 | 공개 재고 계약은 상품 코드 직접 조회가 아니라 키워드 결합형이다. 선택 상품명으로 범위를 좁히고 응답 상품 코드를 검증한다. |
| 이마트24 | 통합 MCP `check_inventory(service=emart24, pluCd=선택코드)` | 같은 조건에서 캐시한 매장 목록을 이용하는 공식 재고 API | 통합 도구에는 `bizNoArr` 인수가 없다. 주 경로 내부의 매장 검색을 앱에서 완전히 분리할 수 없다. 보조 경로의 매장 목록은 별도 캐시한다. |

주 경로는 최신 공개 스키마의 통합 도구 계약을 우선 사용하기 위해 선정했다. 어느 경로가 더 빠르다는 측정에 근거한 선정이 아니다. 구형 브랜드별 이름이 중단됐다고 판단하지 않았으며, 기존 넓은 검색의 호환 경로는 남겨 두었다. 현재 화면의 일반 상품 검색·선택 상품 비교는 새 API를 사용한다. 상품 후보는 한 페이지 최대 20개로 제한하고 더 있을 경우 범위가 일부임을 표시한다.

재고 주 경로의 정상 수량 0과 정상 빈 목록은 성공으로 처리하며 보조 요청을 만들지 않는다. 단, inventory/nearbyStores의 available=False는 빈 목록과 구분해 오류로 처리하고 unavailableReason과 원본 오류 필드를 보존한 뒤 보조 확인한다. `lookup_failures`, 불완전 목록, 해석 불가능한 재고는 보조 확인의 근거다. 중복 점포·상품은 식별 가능한 정보로만 합친다. 같은 자료 시각 또는 시각 미제공 상태에서 수량이 서로 다르면 임의로 최신 값을 고르지 않고 재고 미확인·부분 확인으로 남긴다. 호출 제한 429는 같은 중계 서비스의 보조 요청도 즉시 반복하지 않는다.

## 앱 캐시, 동시 요청과 시각

| 자료 | 기본 보관 시간 | 환경 변수 |
| --- | --- | --- |
| 재고 | 60초 | `CONVENIENCE_INVENTORY_CACHE_SECONDS` |
| 상품 후보 | 900초 | `CONVENIENCE_PRODUCT_CACHE_SECONDS` |
| 매장·행정구역 | 1,800초 | `CONVENIENCE_STORE_CACHE_SECONDS` |
| 행사 | 21,600초 | `CONVENIENCE_PROMOTION_TTL_SECONDS` |
| 재고·상품·매장 오류 뒤 재요청 대기 | 3초 | `CONVENIENCE_FAILURE_COOLDOWN_SECONDS` |

재고 60초는 앱의 짧은 반복 조회를 합치는 기본값이다. 중계 원본의 실시간 갱신 주기를 뜻하지 않는다. 문서에는 CU REST 재고 10분, 이마트24 REST 재고 5분 등의 별도 중계 TTL도 안내돼 있다. 60초 뒤 새로 요청해도 중계가 과거 자료를 반환할 수 있다. 실제 업데이트 주기의 연속 측정은 수행하지 않았다.

같은 세션의 동일 모드·작업 종류·브랜드·상품명·선택 코드·바코드·정밀 좌표·재조회 조건은 진행 중 Future를 공유한다. 반환 자료는 복제해 한 호출자의 수정이 다른 호출자의 결과에 영향을 주지 않는다. 세션별 manager와 임시 저장 위치를 사용하므로 사용자 간 결과·오류를 공유하지 않는다. 다른 상품·다른 위치는 별도 키다. 재고 검색의 부분 오류는 브랜드 전역 변수에 저장하지 않고 각 조회 결과와 캐시 키에 붙인다.

`received_at`은 앱 수신 시각, `source_updated_at`/`stock_source_updated_at`은 제공된 자료 시각, `app_cache_used`는 앱 캐시 사용 여부다. 자료 시각이 없으면 빈 값이다. HTTP 날짜·Age·중계 fetchedAt을 원본 재고 시각으로 만들어 넣지 않는다. 화면의 재고 재조회는 앱 재고 캐시만 우회하고 행사 목록 캐시는 재사용한다. 재조회는 중계·공식 원본을 강제로 갱신하지 않으며 중계·공식 원본까지 강제로 갱신됐다고 표시하지 않는다. 오래된 자료나 캐시를 읽었다고 수신/원본 시각을 새로 붙이지 않는다.

네트워크 연결·시간 초과·일부 서버 오류는 최대 1회 재시도(총 2회)하며 짧게 기다린다. 오류가 반복되면 조건별 대기 시간을 적용한다. 실패 시 가상 CSV로 바꾸지 않는다. 과거 캐시를 참고로 반환하는 경우 `CACHE`로 낮춰 확정 추천에서 제외한다.

## 요청 기록의 범위

manager의 메모리 `metrics` 및 전달된 로그 콜백에는 브랜드, 상품/매장/재고 주·보조 경로, 실제 요청 시도 수, 경과 밀리초, 성공 여부, 보조 사용 여부, 오류 종류를 기록한다. 검색어·위치·인증 헤더·쿠키·토큰은 로그에 기록하지 않는다. 실제 HTTP 횟수는 `McpClient` POST/REST GET 재시도를 포함하며 경로 로그 건수와 구분한다. tools/list 같은 개발 조사 요청, 화면 위치 검색, 행사 수집의 별도 요청은 이 재고 경로 수치에 섞지 않는다. 원본 공개 필드와 구조화된 오류는 인증 관련 키·값을 제거해 `raw_payload`/`DataLoadResult.error_details`에 보존한다. 주 경로 실패 후 보조가 성공해도 최초 오류를 보존한다.

## 제한된 외부 실제 조회

조건: 서울시청 좌표 37.5665, 126.9780, 검색어 신라면. 상품 후보는 최대 3개, 최초 CU 결합 조회의 점포는 최대 3개. 선택 재고 조회는 기존 상한 20개. 이마트24 행정구역은 서울특별시·중구를 명시해 추가 위치 검색을 하지 않았다. 조사 클라이언트는 네트워크 재시도 0회, 전송 제한 12초였으며 자동 테스트와 분리해 아래 요청만 수행했다. 한 번씩의 응답이므로 평균·속도 향상·실제 점포의 재고 정확도를 입증하지 않는다.

브랜드 자료 요청 총 8회: GS25 2회, CU 2회, 세븐일레븐 1회, 이마트24 3회. 별도로 `tools/list` 1회(HTTP 200), 공개 문서 GET 3회를 수행했다. 공식 재고 보조 경로를 포함한 모든 외부 경로의 정상 동작을 확인한 것은 아니다.

- GS25·이마트24 상품 검색에 `standard.products`가 실제 제공됐다. 내부 code/name/price/imageUrl/raw를 활용하되 price는 후보 참고가다.
- 이마트24 `find_stores`에 `standard.stores`가 실제 제공됐다. 재고 수량은 정규화 매장 정보만으로 추정하지 않고 원래 재고 필드에서 읽는다.
- CU 응답과 이마트24 선택 재고 응답에는 이 조사에서 `standard`가 없었으므로 원본 필드를 파싱했다.
- CU 선택 응답 20개 점포와 이마트24 선택 응답 9개 점포를 파싱했지만 원본 재고 자료 시각은 미제공이었다. 새 수신 시각을 원본 재고 시각으로 바꾸지 않았다. 원본 자료의 신선도·점포 확정 가격·행사 조건이 충족되지 않으면 확정 구매 추천을 만들지 않는다.
- GS25는 상품 검색은 성공했지만 선택 재고가 실패했다. 세븐일레븐은 상품 검색 단계에서 중계 502 오류가 관측돼 재고 성공으로 보고하지 않는다. 추가 외부 반복 요청은 하지 않았다.

각 응답/오류의 조사 자료: [limited-live-probes.json](research/limited-live-probes.json). 실제 통합 tools/list의 전체 응답: [tools-list.txt](research/tools-list.txt). 조회 당시 문서 사본은 같은 폴더의 Markdown 3개다.

## 자동 검증과 개선 수치의 해석

관련 검사 `test_live_adapter`, `test_composite_inventory_adapter`, `test_data_manager`, `test_v21_inventory`, `test_v21_inventory_review`: **44개 통과**. 주 성공·정상 0·정상 빈 결과의 보조 생략, 오류 복구, 중복 제거, 같은/다른 조건 동시 요청, 사용자별 격리, 실패 대기, TTL 만료/강제 조회/원본 시각 보존, 개별 캐시 분리, 코드 직접 전달, 유한 재시도, 구조화된 오류 보존·인증값 제거를 검증했다.

모의 정상 단일 조회에서 v2의 두 경로 작업은 2개이고 v2.1은 주 경로 1개·보조 0개다. 보조가 필요한 오류 시에는 두 경로를 사용할 수 있다. 동일 동시 요청 6개는 실제 어댑터 호출 1개로 합쳐지고, 유효 앱 캐시는 원격 호출 0개다. 이 수치는 테스트 조건의 호출 횟수이며 외부 요청 수가 모든 브랜드에서 일률적으로 절반이 된다는 뜻은 아니다. **v2 대비 외부 응답 속도 향상은 미측정**이다. 위 표는 현재 경로의 1회 응답 시간만 기록한다.

전체 테스트·화면 확인 결과는 최종 검증 문서를 참조한다.
