# 편의점 장바구니 비교 서비스 구현 계획

> **구현 담당자 안내:** 체크 항목을 순서대로 진행하고 단계별 검증 결과를 기록한다. 현재 파일은 개발 계획이며 체크되지 않은 항목은 구현 완료를 의미하지 않는다.

**작성일:** 2026년 10월 31일  
**목표:** 중간 과제의 조회와 행사 계산을 활용해 매장별 장바구니 재고·총액·예산을 비교하는 Streamlit 앱을 만든다.  
**구성:** 기존 코드를 `core` 패키지로 옮기고 장바구니 평가를 추가한다. 화면은 Streamlit으로 새로 만들며, 서버에서 사용자별 상태와 임시 캐시를 분리한다.  
**개발 도구:** Python 3.12 권장, Streamlit, pandas, requests, unittest, GitHub, Streamlit Community Cloud.

## 전체 조건

- 작업 위치는 이 문서가 있는 `기말 과제` 폴더다. 중간 과제 원본과 기존 9주차 앱은 수정하지 않는다.
- 한 매장에서 장바구니 전체 구매를 비교한다. 최대 5종, 상품별 1~10개, 비교 매장 최대 10곳, 반경 0.5·1·2km를 기본 범위로 둔다.
- 예산 0원은 제한 없음이다. 실제로 받을 수량은 무료 증정분을 포함하며, 추가 수령은 자동 적용하지 않는다.
- 일반 판매, 1+1, 2+1을 기본 지원한다. 기존 함수의 3+1·정률·정액 할인 구현은 남겨도 기본 UI에서 지원한다고 표시하지 않는다.
- TEST는 고정된 시연 자료, LIVE는 외부 조회다. PARTIAL·CACHE·ERROR와 항목별 상태를 보존하고 LIVE 실패를 TEST로 바꾸지 않는다.
- 가격·재고·행사 미확인은 정상적인 0원·품절·행사 없음과 다르다. 과거 자료와 확인이 부족한 매장은 현재 확정 추천에서 제외한다.
- 코드를 이식한 직후에는 실제 조회 전에 네트워크를 사용하지 않는 테스트로 구조와 계산을 확인한다. LIVE 점검은 별도 단계에서 제한적으로 실행한다.
- GitHub 반영과 배포는 개발 완료 후 별도 실행 단계다. 계획 작성만으로 파일 업로드나 서버 배포가 완료되는 것은 아니다.

## 1 제공된 중간 과제에서 확인한 내용

원본 기준 경로는 `../convenience_store_compare/프로그램/`이다. 아래 경로와 함수는 실제로 확인했으며, 뒤의 `core/`와 `sample_data/` 경로는 앞으로 만들 구조다.

| 기존 파일 | 확인한 기능 | 적용 방향 |
| --- | --- | --- |
| `models.py` | StoreProduct, DataLoadResult, 재고 정확성, 항목별 출처와 상태 | 자료 구조 재사용, 장바구니용 자료 추가 |
| `services/promotion.py` | calculate_purchase_cost와 PromotionCost | 재구현하지 않고 상태 확인을 보완해 호출 |
| `services/product_matching.py` | same_product는 다른 브랜드를 동일 상품으로 보지 않음 | 같은 브랜드의 행사 결합에만 사용 |
| `services/store_matching.py` | 코드·주소·좌표로 매장 판단 | 매장 연결에 재사용 |
| `services/integration_service.py` | 충돌 자료를 제외하고 재고와 행사 결합 | 기존 규칙을 유지하고 근거 표시 |
| `data/data_manager.py` | search_all, 두 조회 경로, 30분 캐시, 가격 미확인 행 제외 | 미확인 행 보존, TTL 지정, 강제 재조회 추가 |
| `data/promotion_manager.py` | 6시간 행사 캐시, 기본 경로에 JSON 저장 | 세션별 경로와 행사 유효성 표시 |
| `services/geocoding.py` | 주소 검색과 IP 위치 추정 | 주소 검색 재사용, IP 위치 추정은 웹에서 제외 |
| `ui/main_window.py` | Tkinter 화면과 지도, 스레드 콜백 | 재사용 대상에서 제외하고 웹 화면 작성 |

| `tests/` | unittest 테스트 함수 39개 | 필요한 테스트 이식과 새 사례 추가 |

기존 테스트의 존재를 확인한 것이며 이번 문서 작성에서 테스트를 실행하지는 않았다. 외부 서비스의 현재 응답도 아직 확인하지 않았다. 초기 Word 기획서의 TEST 자동 전환 설명과 일부 발표 문구는 현재 코드와 차이가 있어 현재 구현을 우선한다.

## 3 공통 인터페이스

새 타입은 `core/cart_models.py`에 정의한다. 나열된 필드는 이후 단계의 공통 계약이다. 외부 상품 자료에 이식 과정에서 임의의 기본값을 추가하지 않고 기존 의미를 유지한다.

```python
CartItem(item_id: str, label: str, quantity: int)
CatalogLink(item_id: str, brand: str, barcode: str,
            product_code: str, product_name: str)
LineEvaluation(item_id: str, quantity: int,
               payable: int | None, reference_payable: int | None,
               stock_state: str, pricing_state: str,
               reason: str, record: StoreProduct | None)
StoreEvaluation(store_key: str, brand: str, store_name: str,
                distance_km: float | None,
                lines: list[LineEvaluation], total: int | None,
                known_subtotal: int, reference_total: int | None,
                eligible: bool, source: str, reasons: list[str])
BasketRecommendations(cheapest: StoreEvaluation | None,
                      nearest: StoreEvaluation | None,
                      over_budget_by: int | None, message: str)
QuerySnapshot(records: list[StoreProduct],
              statuses: list[DataLoadResult],
              statuses_by_item: dict[str, list[DataLoadResult]], context_key: tuple,
              requested_at: str, completed_at: str)
```

`stock_state`는 ENOUGH·SHORT·UNKNOWN, `pricing_state`는 CONFIRMED·REFERENCE·UNKNOWN으로 정의한다. 출처 상태는 TEST·LIVE·PARTIAL·CACHE·ERROR를 유지한다. `known_subtotal`은 금액이 확정된 항목만 합한 값이며 전체 총액으로 표시하지 않는다. `reference_total`은 모든 항목에 확정 또는 일반가 참고 금액이 있을 때만 계산한다.

새 함수는 다음 계약을 사용한다.

```python
# catalog.py
resolve_cart_records(cart: list[CartItem], records: list[StoreProduct],
                     links: list[CatalogLink]) -> dict[str, list[StoreProduct]]
# cart_pricing.py
evaluate_line(item: CartItem, record: StoreProduct | None) -> LineEvaluation
# basket.py
evaluate_stores(cart: list[CartItem], records_by_item: dict[str, list[StoreProduct]],
                user_lat: float, user_lng: float, radius_km: float,
                max_stores: int = 10) -> list[StoreEvaluation]
# basket_recommendation.py
recommend_baskets(stores: list[StoreEvaluation], budget: int) -> BasketRecommendations
# query_service.py
fetch_snapshot(cart: list[CartItem], links: list[CatalogLink],
               manager: DataManager, user_lat: float, user_lng: float,
               brands: list[str], mode: str, force_refresh: bool = False) -> QuerySnapshot
# exporting.py
comparison_csv(stores: list[StoreEvaluation], snapshot: QuerySnapshot) -> bytes
```

기존 위치 인수와 반환 형식은 유지하면서 다음 선택 인수를 추가한다.

```python
DataManager(test_csv, mode="TEST", log=None, cache_path=None,
            cache_ttl_seconds=1800, promotion_manager=None)
DataManager.search_all(keyword, user_lat, user_lng, brands=None, mode=None,
                       *, include_unpriced=False, force_refresh=False)
```

기존 반환값 `tuple[list[StoreProduct], list[DataLoadResult]]`는 유지한다. 새 인수를 생략한 기존 호출은 가격 미확인 행을 제외하고 재고 캐시 30분을 적용한다.

## 단계 3 기존 행사 계산에 확인 상태를 연결한다

**작성:** core/services/cart_pricing.py, tests/test_cart_pricing.py.  
**재사용:** core/services/promotion.py의 calculate_purchase_cost.  
**입력:** CartItem, StoreProduct 또는 미발견을 뜻하는 None.  
**출력:** evaluate_line이 반환하는 LineEvaluation.

- [ ] 1,800원 상품의 1+1은 1개·2개 모두 1,800원, 3개는 3,600원인지 검증한다. 2+1은 2개·3개 모두 3,600원, 4개는 5,400원인지 확인하고 수량 1~10개를 점검한다.
- [ ] 가격 0원, promotion_known=False, stock_known=False, stock_quantity_exact=False, 필요 수량 미만, record=None 사례를 넣는다.
- [ ] `python -m unittest tests.test_cart_pricing -v`로 evaluate_line 미구현에 따른 실패를 확인한다.
- [ ] 요청 수량 q를 실제 받을 수량으로 해석한다. 정확한 재고, 가격, 행사 확인 상태를 판단한 뒤 기존 계산 함수를 호출한다. 기존 함수에는 promotion_known과 stock_quantity_exact 인수가 없으므로 호출 전 확인이 필요하다.
- [ ] 행사가 미확인인데 빈 문자열로 바꿔 확정 계산하지 않는다. 일반가 참고액을 reference_payable로 반환하고 pricing_state=REFERENCE로 둔다. 지원하지 않는 행사도 참고액과 미지원 사유를 보여준다.
- [ ] 추가 무료 상품을 자동으로 더하지 않는다. 재고 판단과 가격 판단은 독립적으로 기록해 가격이 있어도 재고가 부족한 행을 추천에서 제외할 수 있게 한다.
- [ ] 새 테스트와 test_ported_core를 함께 실행해 기존 계산이 바뀌지 않았는지 확인한다.

## 단계 4 매장별 합계와 예산 추천을 만든다

**작성:** core/services/basket.py, core/services/basket_recommendation.py, tests/test_basket.py, tests/test_basket_recommendation.py.  
**입력:** 항목별 매장 상품, CartItem, 기준 위치, 반경, 예산.  
**출력:** StoreEvaluation 목록과 BasketRecommendations.

- [ ] A=5,300원, B=6,500원, 예산 6,000원에서 A 추천과 잔액 700원을 확인하는 테스트를 먼저 작성한다. 잔액은 budget-total로 화면에서 계산하며 over_budget_by는 초과 시에만 양수로 반환한다.
- [ ] 매장은 브랜드·점포 코드로 묶는다. 코드가 없으면 같은 브랜드의 주소와 기존 same_store로 확인한다. 매장 이름만으로 합치지 않는다.
- [ ] 장바구니의 모든 항목에 evaluate_line을 적용한다. 미발견은 UNKNOWN으로 남긴다. 중복 관측은 기존 최신 재고 결합 규칙을 적용하고, 동일 상품·매장의 충돌이 해결되지 않으면 확정 후보에서 제외한다.
- [ ] 기존 haversine_km로 직선거리를 계산하고 반경 밖을 제외한다. 위치가 없어 반경 내 여부를 판단할 수 없는 매장은 별도 참고 표시한다. 10곳을 넘으면 확인된 거리순, 같은 거리에서는 매장 키순으로 선택하고 제외 건수를 표시한다.
- [ ] 모든 행의 가격이 확정됐을 때만 total을 계산한다. known_subtotal은 확정된 행의 소계다. reference_total은 모든 항목에 가격 또는 일반가 참고액이 있을 때만 계산한다.
- [ ] eligible은 모든 행의 필요 수량과 가격·행사가 확인됐고 현재 비교에 쓸 수 있을 때만 참으로 둔다. TEST는 시연 추천, LIVE는 현재 추천으로 구분한다. CACHE는 참고용으로 제외한다. PARTIAL에서도 해당 매장의 모든 항목이 성공했다고 추적되는 경우만 평가하고 실패 범위를 모르면 확정 추천에 넣지 않는다.
- [ ] 예산 이내 후보를 우선한다. 최저가는 총액·확인된 거리·매장 이름순, 가까운 곳은 거리·총액순으로 정한다. 거리가 0인 값을 결측으로 보지 않는다. 예산0, 예산 내 후보 없음, 전체 후보 없음도 검사한다.
- [ ] `python -m unittest tests.test_basket tests.test_basket_recommendation -v`와 `python -m unittest discover -s tests -v`의 오프라인 사례를 확인한다.

## 단계 6 Streamlit 화면과 CSV를 연결한다

**작성:** streamlit_app.py, core/services/exporting.py, tests/test_app.py, tests/test_exporting.py.  
**입력:** 사용자 위치·장바구니·예산, QuerySnapshot, StoreEvaluation.  
**출력:** 한국어 웹 화면과 UTF-8 BOM을 포함한 CSV.

- [ ] 위치는 주소 검색과 위도·경도 직접 입력으로 받는다. 서버에서 locate_by_ip()를 호출해 사용자 위치로 표시하지 않는다.
- [ ] TEST를 명시한 화면에서 시작한다. 상품 추가·삭제·수량을 세션별로 보관한다. 같은 항목 중복 추가는 한 행에 수량을 합치되 합계가10개를 넘으면 변경을 적용하지 않고 안내한다.

- [ ] 비교 버튼만 fetch_snapshot을 호출한다. 장바구니 수정이나 CSV 버튼으로 외부 조회가 다시 실행되지 않게 한다.
- [ ] 추천 매장과 근거, 예산 차액, 대상 매장 수, 직선거리, 자료 시각과 상태를 표시한다. 상품별 부족 사유와 가격 계산 근거를 펼쳐 볼 수 있게 한다.

- [ ] `python -m unittest tests.test_app tests.test_exporting -v`와 `python -m streamlit run streamlit_app.py`로 입력부터 CSV까지 확인한다.

## 4 시간 배분과 진행 기록

아래는 1회60~90분의 작업을 가정한 권장 배분이다. 제출 일정이 아니며 외부 서비스 조사가 길어지면 연동 부분을 별도로 조정한다.

| 작업 회차 | 단계 | 목표 |
| --- | --- | --- |
| 1~2회 | 1~2 | 기존 계산 이식과 시연CSV 연결 |
| 3~4회 | 3~4 | 금액·재고·예산별 매장 평가 |
| 5~6회 | 5 | 여러 상품 조회, 캐시와 세션 분리 |
| 7~8회 | 6 | TEST에서 상품 선택부터 CSV까지 동작 |
| 9회 이후 | 7 | 실제 조회 확인과 배포·발표 준비 |

작업을 마칠 때 변경 파일, 실행한 확인, 결과, 다음 항목을 짧게 기록한다. 코드 변경마다 관련 테스트를 우선 확인하고 필요한 범위의 통합 검증을 수행한다. Git 커밋과 외부 공개는 실제로 해당 작업을 의뢰받은 단계에서 진행한다.

아직 정해지지 않은 것은 제출일과 확보할 수 있는 제작 시간, 실제로 LIVE 연결이 가능한 브랜드다. 일정은 단계별 시간 배분에 반영하며, 지원 브랜드는 실제 조회 결과에 따라 명시한다. 모든 브랜드의 LIVE 지원과 장기 가격 기록용 데이터베이스는 기본 완료 조건에 추가하지 않는다. 구현은 이 문서의 체크 항목을 바탕으로 다음 작업에서 진행한다.
